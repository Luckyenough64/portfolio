Debugging memory pressure in distributed analytics

Cases where a memory error is a symptom of data distribution or operation order.

2.7M requests4 executors12 GB per executor

Why raising limits does not explain the cause

“The job ran out of memory.”
“Let's add more memory.”

This response is reasonable, and sometimes necessary. But it tests capacity, not causality. If the computation creates an avoidable concentration of data, a larger limit only moves the failure threshold.

Why the error appears in memory

Memory is where the consequences of earlier choices accumulate: wide joins, excessive shuffle, late filters, skewed keys, and inefficient pipeline stages.

The visible failure may therefore be far from the operation that caused it. A write stage can fail because of repartitioning, while the underlying imbalance began several transformations earlier.

A recurring pattern

Across Spark, Vertica, ClickHouse, and large ETL workloads, I have seen the same sequence: a job fails, limits are increased, the error disappears, data grows, and the error returns at a higher cost.

This does not mean resources are irrelevant. It means the resource change should remain a hypothesis while the computation model is inspected.

Case: data volume did not explain the failure

One workload combined about 2.7 million support records, 866 thousand service attributes, more than 600 thousand user events, and several reference datasets.

The configuration already looked comfortable: four executors, ten cores each, 8 GB executor memory, and 4 GB memory overhead. Yet failures continued.

The total input was moderate for a distributed system. The expensive part was how data moved between nodes.

The cost of moving data

JOIN, GROUP BY, DISTINCT, and window functions can all trigger large exchanges between machines. Network transfer, serialization, and intermediate buffers consume resources before the final result exists.

A table of a few gigabytes can generate tens or hundreds of gigabytes of network exchange.

The consequence of one line

df.repartition(1)

This command is often used to produce a single output file. It also asks the cluster to concentrate the final dataset in one partition.

  • a large shuffle;
  • one overloaded executor;
  • higher memory use;
  • a much longer write stage.

In several jobs, this final redistribution cost more than the main computation.

When more memory only helps temporarily

If a pipeline needs 100 GB and the limit is raised to 200 GB, it may complete. If the demand comes from an architectural pattern, normal data growth eventually consumes the new margin.

I therefore separate two questions: does the workload have enough resources, and does it need to hold this much data at once?

When the failure appears at the end

A pipeline may run for hours and fail while writing the result. Final serialization, aggregation, file sizing, or repartitioning can create a new peak after the visible calculations are complete.

Memory errors often surface far from their actual source.

What I check first

diagnosis

Data skew

One executor receives far more data than the rest.

diagnosis

Excessive shuffle

The system spends more resources moving data than processing it.

diagnosis

Late filtering

Rows survive expensive stages even though they could be removed earlier.

diagnosis

Operation order

Changing join and filter order can sharply reduce intermediate data.

The question I start with

Instead of asking only why the system has no memory left, I ask:

Why does the system need to hold so much data at the same time?

That formulation usually points toward distribution, intermediate state, or ordering.

Memory pressure as a diagnostic signal

A memory error is evidence about the shape of a computation. It may indicate skew, unnecessary state, an expensive exchange, or a storage-model constraint.

A memory failure is a reason to inspect data distribution and preceding stages, not only the limit.

What memory pressure taught me

01

Memory is rarely the root cause

It often exposes a deeper issue.

02

Shuffle is easy to underestimate

Reducing exchange can help more than adding executors.

03

Skew creates a local bottleneck

This can happen with moderate total volume.

04

Architecture matters more than limits

Resources create headroom; computation changes alter the curve.

05

Good diagnosis starts with “why”

Look for the mechanism, not only the exhausted component.

06

The cause may precede the failure

Inspect several earlier stages.

Conclusion

Many serious performance problems improved after changing join order, filtering earlier, reducing skew, limiting shuffle, or revisiting the processing model.

In distributed systems, the place that fails is not necessarily the stage that introduced the cause.

Memory pressure is useful as a diagnostic signal, not just a request for a higher limit.
